# Workflow Capability Reference

- Top-level fields: `name`, `version`, `description`, `tags`, `category`, `variables`, `variable_types`, `agents`, `workflow`, `error_handling`, `timeout`, `directory_isolation`, `concurrency`, `knowledge_base`, `code_preamble`, `global_agent`, `module`
- Agent authoring baseline: generated workflows should explicitly set `session_id_strategy` on every top-level agent, every `agent_based.orchestrator`, and `global_agent.agent`
- Step modes (seven exclusive primary modes): single-agent, `group_chat`, `agent_based`, `code`, `classifier`, `state_machine`, `sub_workflow`
- Common extensions: `depends_on`, `condition`, `priority`, `retry`, `manual_approval`, `timeout_seconds`, `parallel`, `repeat_until`, `extract`, `iterate_over`, `aggregate`, `on_success`, `on_failure`
- Hard constraints:
  - `parallel` only for single-agent steps
  - `repeat_until` not for `code` / `agent_based` / `sub_workflow`
  - `iterate_over` only for single-agent / `code`
  - `iterate_over` cannot combine with step-level `parallel`, `retry`, `repeat_until`, `manual_approval`, `timeout_seconds`
  - `state_machine` outer step must not use `parallel`
  - `state_machine` inner steps cannot use outer `retry / parallel / manual_approval`
  - `sub_workflow` cannot combine with `parallel` / `iterate_over` / `repeat_until` (v1)
  - runtime `condition` supports simple `var op value` (`==`, `!=`, `>`, `<`, `>=`, `<=`, `contains`)
  - sequentially reused agents usually need `session_id_strategy: per_execution`
  - `iterate_over`, step-level `parallel`, and obvious fan-out branches usually need `session_id_strategy: auto`
  - `global_agent.agent` and `agent_based.orchestrator` should usually use `session_id_strategy: per_execution`
  - avoid `per_agent` / `fixed` unless the user explicitly needs cross-execution memory or a fixed session id
- Built-in agent presets: `universal`, `universal_reasoning`, `coder`, `researcher`, `writer`, `data_analyst`, `asa`, `pdf_processor`, `lightweight`, `chat`, `office_document`, `word_document`, `excel_workbook`, `powerpoint_presentation`, `multimedia_creator`, `devops`, `communication`, `web_scraper`, `computer_operator`
- Code step languages (`CodeStepConfig.SUPPORTED_LANGUAGES`): `python`, `javascript`, `typescript`, `bash`, `ruby`, `lua`, `cli`
- Aggregate strategies (`AggregateConfig.SUPPORTED_STRATEGIES`): `concat`, `json_array`, `numbered_list`, `pick_longest`, `pick_shortest`
- Knowledge base providers: `openai`, `ollama`
- Authoritative validation:
  - `braidrun-agent -V workflow.yaml`
  - `workflow.validateWorkflow`
  - `WorkflowParser.validateWorkflow`
- Must-read reference templates:
  - Core: `workflows/templates/test-workflow-minimal.yaml`, `test-workflow-simple.yaml`, `test-workflow-sequential.yaml`, `test-workflow-parallel.yaml`, `test-workflow-condition.yaml`, `test-workflow-variables.yaml`
  - Modes: `test-workflow-group-chat.yaml`, `test-workflow-agent-based.yaml`, `test-workflow-code-steps.yaml`, `test-workflow-classifier.yaml`, `test-workflow-state-machine.yaml`
  - Extensions: `test-workflow-repeat-until.yaml`, `test-workflow-extract.yaml`, `test-workflow-iterate-over.yaml`, `test-workflow-aggregate.yaml`, `test-workflow-fan-out.yaml`, `test-workflow-error-handling.yaml`, `test-workflow-full-features.yaml`, `test-workflow-all-features.yaml`
  - Runtime: `test-workflow-knowledge-base.yaml`, `test-workflow-long-running.yaml`, `test-workflow-session-sharing.yaml`, `test-workflow-multi-preset.yaml`, `test-workflow-skill-testing.yaml`
  - Production references (in `workflows/templates/`): `code-review.yaml`, `prd-review-refinement.yaml`, `workflow-generator.yaml`, `approval-lifecycle-state-machine.yaml`
- `code_preamble`: keyed by language. Each language entry uses `inline` OR `ref` (mutually exclusive). Engine prepends matching language preamble to every `code` step. Example:
  - `code_preamble: { python: { ref: "./skills/braidrun_workflow_utils.py" }, bash: { inline: "set -euo pipefail" } }`
- `agent_based.orchestrator` may set either `preset` or `agent` (referencing a top-level agent declared in `workflow.agents`), never both. Circular references raise `Circular agent reference detected`.
- `manual_approval` is a step **enhancement** in YAML, not a primary mode. The Web editor exposes a 7th "manual_approval" primary type that lands as a step with `manual_approval.enabled = true` and no other main mode attached.
- `directory_isolation` patterns support placeholders: `{base_dir}`, `{execution_id}`, `{step_name}`, `{agent_name}`, `{workflow_name}`.
- `concurrency.max_concurrency` is the **intra-workflow** topology-layer parallelism. CLI `--workflow-max-concurrency` is the **inter-workflow** batch parallelism. Do not conflate them.
- `sub_workflow`: 7th primary step mode. References another saved workflow. Reference identity = `workflow_id` | `path` | `name` (exactly one). Version strategy: `latest` | `pinned` (with `pinned_version`). Default isolation: independent child `WorkflowExecutionContext`, isolated KB, no agent inheritance. Resolver-based:
  - CLI auto-uses `FileSystemWorkflowResolver(parentDir)`.
  - Host services may inject a custom resolver (e.g. database-backed with version pinning).
  - Static cycle detection via DFS through resolver. Runtime cycle detection via ThreadLocal stack. Default `max_sub_workflow_depth = 8`.
  - Strict mode (child has `module` contract): inputs/outputs must match contract. Loose mode (no contract): parent maintains `required_inputs` list.
- `module`: optional top-level field declaring this workflow as a reusable module. Schema: `{ enabled, display_name, description, category, icon, tags, contract_version, deprecated, deprecation_note, inputs: ModuleInputSpec[], outputs: ModuleOutputSpec[], examples: ModuleUsageExample[] }`.
  - `ModuleInputSpec`: `{ name, type, required, default?, description?, example?, maps_to_variable?, allowed_values?, min?, max? }`. Types: `string` / `number` / `boolean` / `path` / `json` / `list` / `enum`.
  - `ModuleOutputSpec`: `{ name, type, description?, source }`. `source` is a template expression resolved against the child context (e.g., `"{{var:final_path}}"` or `"{{steps.gen.output}}"`).
  - Contract evolution: comparing contracts detects breaking changes (new required input / removed output / type change).
